# Решение

## Что изменено

### Скидки

Добавлена поддержка `amountPaid` из внешнего API.

- в таблицу `orders` добавлено поле `amount_paid_kop`
- теперь в базе хранятся как исходная сумма заказа, так и фактически оплаченная сумма
- `GET /customers/:id/daily-totals` теперь возвращает:
    - `gross` - сумма заказов до скидки
    - `discount` - размер скидки
    - `net` - фактически оплаченная сумма
    - `total` - сохранен для обратной совместимости и равен `gross`
- внутри приложения денежные значения по-прежнему хранятся в копейках
- в ответ API суммы преобразуются обратно в рубли

Поле `amountPaid` у внешнего API может отсутствовать для некоторых заказов, в том числе для неоплаченных. Поэтому такие заказы принимаются, а при отсутствии `amountPaid` используется значение `0`.

### Часовые пояса

Исправлена ошибка при расчете дневных сумм для часовых поясов, в которых происходит переход на летнее/зимнее время.

В исходной реализации смещение часового пояса вычислялось один раз для текущей даты и затем использовалось для всех заказов:

```ts
const offset = tzOffsetMinutes(timezone, new Date());
```

Это неправильно для исторических данных: UTC-смещение клиента может зависеть от даты самого заказа.

Теперь смещение рассчитывается отдельно для каждого заказа по его `createdAt`:

```ts
tzOffsetMinutes(timezone, o.createdAt)
```

Благодаря этому каждый заказ относится к правильному календарному дню в часовом поясе клиента.

## Причина расхождения

Расхождение, найденное аналитиком у клиента `c_7`, было вызвано использованием одного и того же UTC-смещения для всех исторических заказов.

Проблема проявлялась в конце марта, во время перехода на летнее время.

Например, если текущее смещение часового пояса отличается от смещения в момент создания старого заказа, заказ, находящийся рядом с локальной полночью, может быть отнесен к соседнему календарному дню.

После изменения расчета смещения по `createdAt` суммы за проблемные даты совпадают.

Для предотвращения регрессии добавлен отдельный тест на переход `Europe/Berlin` на летнее время 29 марта 2026 года.

## Тесты

Добавлены и обновлены тесты для:

- расчета `gross`, `discount` и `net`
- обратной совместимости поля `total`
- обработки `amountPaid`
- перехода на летнее время
- существующего поведения дневной агрегации


## result.json

`result.json` сформирован на чистой базе после выполнения полного сценария синхронизации:

1. запуск PostgreSQL и внешнего API
2. выполнение миграций
3. запуск сервиса
4. выполнение `POST /sync`
5. отправка webhook-обновлений
6. запрос:

```text
GET /customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31
```

Полученный ответ сохранен в `result.json`.

## Что еще обнаружено

Внешний API может возвращать заказы без `amountPaid`, в том числе неоплаченные. Поэтому отсутствие этого поля не считается ошибкой валидации.

Также не изменялись:

- сигнатура `createContainer(db, api)`
- интерфейс `OrdersApi`

## Допущения

- `amount` - исходная сумма заказа до скидки
- `amountPaid` - фактически оплаченная сумма
- `total` для обратной совместимости равен `gross`
- `discount = gross - net`
- денежные значения внутри приложения хранятся в целых копейках
- группировка заказов по дням выполняется в часовом поясе клиента
- для определения локальной даты используется `createdAt` заказа

## Использование AI

AI использовался в процессе разработки для анализа существующего кода, поиска причины расхождения в расчетах, обсуждения вариантов реализации и подготовки тестов.

После внесения изменений решение было проверено локальным тестовым набором проекта.
